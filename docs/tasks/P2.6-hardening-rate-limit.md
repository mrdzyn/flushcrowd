## 2. Architecture Reconciliation & The Direct-Write Bypass

### 2.1 Closing the Direct-Write Bypass
Currently, `firestore.rules` allows authenticated client SDKs to create public restrooms and private contributions directly:
```javascript
match /restrooms/{restroomId} {
  allow create: if isAuthenticated() && ... && isValidRestroomCreate(restroomId);
}
match /contributions/{contributionId} {
  allow create: if isAuthenticated() && ... && isValidContributionCreate(contributionId);
}
```

**The Vulnerability:** If client SDKs retain direct write access to Firestore, any malicious user or script can bypass the Cloud Function and submit unbounded writes directly to Firestore, rendering the Cloud Function rate-limiter completely toothless.

**Enforceable Migration Path:**
1. **Staging Parity During Validation:** While the Cloud Function and Flutter callable adapter are implemented on `phase-2/p2.6-hardening`, staging retains the existing direct batch write path for testing.
2. **Production Release Gate (Exclusive Server Boundary):** For production release, direct client `create` permissions on `/restrooms` and `/contributions` MUST BE DISABLED in `firestore.rules` (`allow create: if false;` or restricted via environment checks). All production restroom creations must execute exclusively through the trusted Cloud Function using the Firebase Admin SDK.
3. **Emulator Test Requirement:** Explicit rules emulator tests in `rules_tests/test/` must verify that client SDK direct `setDoc` / `batch.commit` attempts to `/restrooms` and `/contributions` fail with `PERMISSION_DENIED` under the enforced production configuration.

### 2.2 Technical Evaluation: Option A vs Option B Across 9 Vectors

| Architectural Vector | Option A: Trusted Cloud Function (Firebase Admin SDK) | Option B: Firestore Security Rules (Deterministic Slot Docs) | Verdict / Requirement |
| :--- | :--- | :--- | :--- |
| **1. Policy & Rolling Windows** | **PASS.** Private `rateLimits/{uid}` maintains timestamp array. Transaction filters `t => now - t < 24h` and `t => now - t < 10m`, rejecting if >= 10 or >= 3, and prunes expired entries. | **FAIL.** Rules cannot execute collection queries, range scans, or array filtering. Fixed 10m slots allow boundary bursts (e.g., 3 at 10:09, 3 at 10:11 = 6 in 2m). Checking 24 hourly slots exceeds the 10 `get()` rules quota. | **Option A Required.** Rules cannot express dual rolling windows. |
| **2. Authoritative Time** | **PASS.** Uses `admin.firestore.Timestamp.now()` or server monotonic clock. Client cannot falsify time. | **FAIL.** Client constructs the slot path in batch requests; manipulating device time targets future slots to bypass limits. | **Option A Required.** Protects against client clock tampering. |
| **3. Concurrent Writes & Atomicity** | **PASS.** Evaluated inside `db.runTransaction()`. Firestore transaction implements Optimistic Concurrency Control (OCC) on `rateLimits/{uid}`, serializing rapid parallel calls. | **FAIL.** Client batches evaluate `!exists()` in parallel before either commits, allowing concurrent bursts to race and slip through rules. | **Option A Required.** True OCC serialization. |
| **4. Document ID Manipulation** | **PASS.** Server derives `/contributionRateLimits/${request.auth.uid}` from verified auth token. Client sends only domain payload. | **FAIL.** Client determines batch document paths. If slot keys are used, malicious clients can manipulate paths or skip slots. | **Option A Required.** Zero client control of auth paths. |
| **5. Rules Access-Call Quota** | **PASS.** Firebase Admin SDK operates in trusted mode and bypasses Security Rules 10-call evaluation limit. | **FAIL.** Phase 2 batch already consumes 4–7 `get()`/`exists()` calls. Rules have a hard cap of 10 calls total. | **Option A Required.** Prevents hitting rule quota limits. |
| **6. Anonymous UID Recreation** | **PASS.** Pairs per-UID rate limiting with Firebase App Check, token age checks (`request.auth.token.auth_time`), and optional IP rate limiting at Cloud Run ingress. | **FAIL.** Rules cannot inspect headers or token age. An automated script simply calls `signInAnonymously()` in a loop to bypass rules. | **Option A Required.** Layered defense against identity recycling. |
| **7. App Check Integration** | **PASS.** Callable Functions support `enforceAppCheck: true` and `consumeAppCheckToken: true`, preventing token replay. | **PARTIAL.** Firestore supports project-level App Check, but cannot do granular per-endpoint token consumption. | **Option A Superior.** |
| **8. Reconciliation & Idempotent Retries** | **PASS.** Function checks if `restrooms/${command.restroomId}` already exists with matching UID; returns existing record without incrementing rate limit. | **FAIL.** If a network drop occurs after batch commit, client retry with the same ID may be blocked if the slot doc was written, breaking idempotent retry. | **Option A Required.** Server-level idempotency preserves stable ID contract. |
| **9. Infrastructure Cost & Complexity** | **PASS.** Cloud Functions V2 free tier covers 2M invocations/month. Requires Blaze plan, but minimal cost at MVP scale. Reuses boundary for Phase 4. | **PASS.** Zero compute cost, but fails security compliance. Saving zero dollars for a non-working policy is invalid engineering. | **Option A Selected.** Inexpensive, reliable, extensible. |

## 3. Implementation Contracts

### P2.6-A — Serverless Backend Service Boundary (Firebase Functions V2)

1. Scaffold TypeScript Cloud Functions V2 project in `functions/`:
   - Runtime: Node.js 20 or 22 (`firebase-functions` v5+, `firebase-admin` v12+).
   - TypeScript strict mode enabled.
2. Implement `submitRestroom` HTTPS Callable Function with V2 signatures:
   ```typescript
   import { onCall, HttpsError, CallableRequest } from 'firebase-functions/v2/https';
   import * as admin from 'firebase-admin';

   export interface SubmitRestroomPayload {
     restroomId: string;
     name: string;
     latitude: number;
     longitude: number;
     geohash: string;
     accessType: 'free' | 'paid' | 'customer_only' | 'key_required';
     // ... complete validated domain fields
   }

   export const submitRestroom = onCall(
     {
       enforceAppCheck: true,        // Verified via App Check in staging/production
       consumeAppCheckToken: false,  // Set true if replay protection is active
     },
     async (request: CallableRequest<SubmitRestroomPayload>) => {
       // 1. Authenticate caller
       if (!request.auth || !request.auth.uid) {
         throw new HttpsError('unauthenticated', 'User must be authenticated anonymously.');
       }
       const uid = request.auth.uid;

       // 2. Validate App Check (when enforced)
       if (process.env.ENFORCE_APP_CHECK === 'true' && !request.app) {
         throw new HttpsError('failed-precondition', 'App Check verification failed.');
       }

       // 3. Pre-transaction validation of request.data
       const data = request.data;
       validateRestroomPayload(data);

       const db = admin.firestore();
       const now = admin.firestore.Timestamp.now();
       const nowMs = now.toMillis();

       // 4. Atomic Transaction Execution
       return await db.runTransaction(async (transaction) => {
         const publicRef = db.collection('restrooms').doc(data.restroomId);
         const privateRef = db.collection('contributions').doc(`restroom_${data.restroomId}`);
         const rateLimitRef = db.collection('contributionRateLimits').doc(uid);

         // Step 4a: Idempotency & reconciliation check
         const publicSnap = await transaction.get(publicRef);
         if (publicSnap.exists) {
           const privateSnap = await transaction.get(privateRef);
           if (privateSnap.exists && privateSnap.data()?.userUid === uid) {
             // Idempotent retry: return existing restroom without charging rate limits
             return { success: true, restroom: publicSnap.data(), isIdempotentRetry: true };
           }
           throw new HttpsError('already-exists', 'A restroom with this ID already exists.');
         }

         // Step 4b: Rate limit evaluation
         const rateLimitSnap = await transaction.get(rateLimitRef);
         const existingTimestamps: admin.firestore.Timestamp[] =
           rateLimitSnap.exists ? (rateLimitSnap.data()?.submissionTimestamps || []) : [];

         const valid24h = existingTimestamps.filter((t) => nowMs - t.toMillis() < 24 * 60 * 60 * 1000);
         const valid10m = valid24h.filter((t) => nowMs - t.toMillis() < 10 * 60 * 1000);

         if (valid24h.length >= 10) {
           throw new HttpsError('resource-exhausted', 'Daily submission limit reached (max 10 per 24 hours).');
         }
         if (valid10m.length >= 3) {
           throw new HttpsError('resource-exhausted', 'Burst submission limit reached (max 3 per 10 minutes).');
         }

         // Step 4c: Atomic batch writes
         const publicPayload = buildPublicRestroomDoc(data, now);
         const privatePayload = buildPrivateContributionDoc(data, uid, now);
         const updatedTimestamps = [...valid24h, now];

         transaction.set(publicRef, publicPayload);
         transaction.set(privateRef, privatePayload);
         transaction.set(rateLimitRef, {
           userUid: uid,
           submissionTimestamps: updatedTimestamps,
           updatedAt: now,
         });

         return { success: true, restroom: publicPayload, isIdempotentRetry: false };
       });
     }
   );
   ```
3. Rate-Limit State Privacy:
   - Collection `/contributionRateLimits/{uid}` is strictly internal.
   - In `firestore.rules`:
     ```javascript
     match /contributionRateLimits/{uid} {
       allow read, write: if false; // Accessible ONLY via Firebase Admin SDK
     }
     ```

### P2.6-B — Flutter Mutation Adapter & Fail-Closed Integrity

1. Implement `CallableFirestoreMutationAdapter` implementing the existing `FirestoreMutationAdapter`:
   - Invokes `submitRestroom` via Firebase Functions client SDK (`FirebaseFunctions.instance.httpsCallable('submitRestroom')`).
   - Translates `FirebaseFunctionsException` to canonical `RepositoryException`:
     - `resource-exhausted` → `RepositoryException('Submission limit reached. Please try again later.', code: 'rate-limited')`.
     - `failed-precondition` / `unauthenticated` → mapped to existing auth / App Check error codes.
2. **Fail-Closed Guarantee:**
   - If the callable function fails for any reason (rate limit, authorization, network), the adapter throws immediately.
   - **Under NO circumstances shall the Flutter client fall back to direct Firestore `WriteBatch` writes.** Falling back to direct writes would bypass server rate limits.
3. **Draft Preservation & UX:**
   - Existing `MainShellScreen` single-flight lock (`_isSubmitting = true`) is preserved.
   - On `rate-limited` error, preserve the draft command, restroom ID, coordinates, and advisory scan notes. Surface a truthful, non-blocking SnackBar with a `Resume` action so the user does not lose entered data.

### P2.6-C — Comprehensive Emulator Test Suite

Author tests in `functions/test/rate_limit.test.ts` (using `@firebase/rules-unit-testing` or Firebase Functions test SDK against the local emulator suite):
1. **Initial Submission:** Verify new UID successfully writes restroom, contribution, and creates rate-limit document with 1 timestamp.
2. **Rolling 10-Minute Burst Limit:** Submit 3 restrooms within 10 minutes (all succeed). 4th submission within 10 minutes is rejected with `resource-exhausted`.
3. **Rolling 24-Hour Daily Limit:** Submit 10 restrooms spaced 15 minutes apart (all succeed). 11th submission within 24 hours is rejected with `resource-exhausted`.
4. **Boundary Timestamps:** Verify a submission at `now + 10m01s` succeeds after a 3-burst; verify a submission at `now + 24h01m` succeeds after 10 daily submissions.
5. **Timestamp Pruning:** Verify timestamps older than 24 hours are pruned from `/contributionRateLimits/{uid}` array on subsequent writes.
6. **Concurrent Submissions:** Fire 5 simultaneous `submitRestroom` calls for the same UID. Exactly 3 succeed, 2 fail with `resource-exhausted` via transaction OCC serialization without data corruption.
7. **Idempotency with Stable ID:** Retry submission with identical `command.restroomId` and same UID. Returns success immediately without adding an entry to `submissionTimestamps`.
8. **Document ID Collision:** Attempt to submit with a `restroomId` already owned by a different UID. Rejects with `already-exists` / `permission-denied`.
9. **Forged / Missing Identity:** Call function without authentication context. Rejects with `unauthenticated`.
10. **Direct Write Bypass Prevention:** Direct client SDK `setDoc` to `/restrooms/{id}` fails with `PERMISSION_DENIED` under enforced rules.

### P2.6-D — App Check & Abuse Guarantees Realism

1. **What App Check Guarantees:**
   - Cryptographically verifies that requests originate from authentic FlushCrowd Android (Play Integrity) and iOS (App Attest) binaries.
   - Blocks automated API scrapers, curl scripts, and off-device bots that lack valid device attestation.
2. **What App Check Does NOT Guarantee:**
   - **App Check does NOT eliminate anonymous UID recreation.** A user or script running inside a genuine app instance on an authentic device can invoke `signInAnonymously()` multiple times to acquire new UIDs.
3. **Multi-Layered Abuse Defense:**
   - Layer 1: App Check blocks off-device and emulator spoofing.
   - Layer 2: Per-UID rate limiting (10/24h, 3/10m) stops in-session spam.
   - Layer 3: Anonymous account creation monitoring; Cloud Run IP throttling limits rapid requests from identical network origins.
   - Layer 4: Replay protection via `consumeAppCheckToken: true` where supported.
4. **Client Handling:**
   - If App Check fails (unsupported device, root, expired attestation), client catches error and displays: `"App verification failed. Please ensure you are using the official app."` Draft is safely preserved.

### P2.6-E — Realistic Financial & Infrastructure Cost Model

Do NOT claim guaranteed zero-cost operation. While early MVP volume operates mostly within free quotas, Cloud Functions V2 has specific billing prerequisites:

1. **Firebase Blaze Plan Requirement:**
   - Cloud Functions V2 runs on Google Cloud Run and **strictly requires a Blaze (pay-as-you-go) billing account**. Deployment cannot occur on the free Spark plan.
2. **Component Cost Breakdown:**
   - **Cloud Functions / Cloud Run:** 2,000,000 invocations and 360,000 GB-seconds free per month. At early MVP volume (e.g., 500–5,000 submissions/month), compute charges are effectively $0.00.
   - **Artifact Registry (Container Storage):** Function deployments generate Docker container images stored in Google Artifact Registry. Image storage incurs minimal monthly charges (~$0.05 to $0.20/month per region), which are not covered by the compute free tier.
   - **Cloud Firestore Mutations:** Each successful submission performs 1 read (rate limit doc) + 3 writes (public restroom, private contribution, rate limit doc). 5,000 submissions/month = 15,000 writes/month, well within the 20,000 free writes/day allowance.
   - **Network Egress:** Minimal JSON payload transfer; covered by standard 10 GB/month free egress.
3. **Budget Safeguards:**
   - Google Cloud billing budget alerts must be configured (e.g. alert thresholds at $5.00 and $10.00/month) before production deployment to prevent unexpected cost escalations.
