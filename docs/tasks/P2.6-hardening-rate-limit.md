### Locked Policy Constraints (`docs/03-privacy-security.md`):
- **Maximum 10 restroom submissions per UID per rolling 24 hours.**
- **Maximum 3 restroom submissions per UID per rolling 10 minutes.**
- **Enforceable server-side controls required before opening production contribution writes.**
- A disabled client-side button or debounce is UX protection, not security. Client-side checks alone are strictly insufficient for production release.

## 2. Rate-Limiting Architecture Reconciliation

### 2.1 Technical Evaluation: Option A vs Option B

| Architectural Vector | Option A: Trusted Cloud Function (Firebase Admin SDK) | Option B: Firestore Security Rules (Deterministic Slot Docs) | Verdict / Requirement |
| :--- | :--- | :--- | :--- |
| **1. Exact Policy Compliance & Rolling Windows** | **PASS.** Stores array of submission timestamps in private `rateLimits/{uid}`. In a server transaction, dynamically filters `timestamps.filter(t => now - t < 24h)` and `timestamps.filter(t => now - t < 10m)`. Automatically prunes expired timestamps. | **FAIL.** Security Rules cannot perform collection queries, range scans, or list iterations. Fixed time slots create boundary-burst vulnerabilities (e.g., 3 writes at 10:09 and 3 at 10:11 violates 10m rolling window). Checking 24 hourly slots exceeds the 10 `get()` quota limit. | **Option A Required.** Rules cannot express rolling dual-window policies. |
| **2. Server-Authoritative Time** | **PASS.** Relies exclusively on `admin.firestore.Timestamp.now()` or server monotonic clock. Client cannot falsify time. | **FAIL.** Client provides the document ID or slot key in the batch request. Malicious client can manipulate device clock or target future slots to bypass slot locks. | **Option A Required.** Protects against client-clock tampering. |
| **3. Concurrent Writes & Atomicity** | **PASS.** Executed inside `db.runTransaction()`. Firestore transaction implements Optimistic Concurrency Control (OCC) on `rateLimits/{uid}`, serializing rapid parallel calls from the same UID. | **FAIL.** Client batch writes evaluate `!exists()` in parallel before either commits, allowing concurrent bursts to race and slip through rules. | **Option A Required.** True OCC serialization. |
| **4. Client Manipulation of Document IDs** | **PASS.** Server derives `rateLimits/${context.auth.uid}` directly from the cryptographically verified auth token. Client transmits only domain payload. | **FAIL.** Client determines batch document paths. If slot keys are used, complex regex is required and still susceptible to parameter pollution. | **Option A Required.** Zero client control of auth paths. |
| **5. Batch Document-Access Limits** | **PASS.** Firebase Admin SDK operates in trusted mode and bypasses Security Rules 10-call evaluation limit. | **FAIL.** Phase 2 batch already consumes 4–7 `get()`/`getAfter()`/`exists()` calls across `restrooms` and `contributions`. Rules have a hard cap of 10 calls total. | **Option A Required.** Prevents hitting rule quota limits. |
| **6. Anonymous UID Recreation Abuse** | **PASS.** Combines Firebase App Check verification (Play Integrity / App Attest) with token age checks (`auth.token.auth_time`) and optional IP rate limiting at Cloud Run ingress. | **FAIL.** Rules cannot inspect IP addresses, headers, or token age. An attacker script simply calls `signInAnonymously()` in a loop to bypass rules. | **Option A Required.** Layered defense against identity recycling. |
| **7. App Check Integration** | **PASS.** Callable Functions support `enforceAppCheck: true` and `consumeAppCheckToken: true`, preventing token replay. | **PASS/PARTIAL.** Firestore supports project-level App Check, but cannot do granular per-endpoint token consumption. | **Option A Superior.** |
| **8. Repository Reconciliation & Idempotent Retries** | **PASS.** Function checks if `restrooms/${command.restroomId}` already exists with matching UID. If found, returns existing record without incrementing rate limit. | **FAIL.** If a network drop occurs after batch commit, client retry with the same ID may be blocked if the slot doc was written, breaking idempotent retry. | **Option A Required.** Server-level idempotency preserves stable ID contract. |
| **9. Infrastructure Cost & Complexity** | **PASS.** Google Cloud Functions V2 free tier provides 2,000,000 invocations/month. Zero cost at MVP scale. Reuses same backend boundary for Phase 4 moderation. | **PASS.** Zero serverless compute, but fails security compliance. Saving zero dollars for a non-working policy is invalid engineering. | **Option A Recommended.** Inexpensive, reliable, extensible. |

### 2.2 Architectural Decision
**Option A (Trusted Firebase Callable Function with Transactional Rate Limiting)** is the canonical implementation selected for Milestone P2.6.

Option B is formally rejected because Firestore Security Rules cannot mathematically or architecturally enforce the locked rolling dual-window policy (10/24h and 3/10m) and cannot prevent concurrent write races or anonymous identity recreation.

## 3. Implementation Contracts

### P2.6-A — Serverless Backend Service Boundary (`functions/`)
1. Create a minimal TypeScript Firebase Functions project in `functions/`:
   - Node.js 20 / 22 runtime with Cloud Functions V2.
   - Dependencies: `firebase-admin`, `firebase-functions`.
2. Implement `submitRestroom` HTTPS Callable Function:
   - Enforce authentication: caller must have valid `context.auth.uid`.
   - Enforce App Check: reject calls missing valid App Check tokens when enabled in staging/production.
   - Run transactional mutation (`db.runTransaction`):
     1. **Idempotency check:** Inspect `restrooms/${command.restroomId}`. If it exists and matches the caller's contribution in `contributions/restroom_${command.restroomId}`, return success immediately without charging rate limits.
     2. **Rate-limit inspection:** Read `/contributionRateLimits/${context.auth.uid}`:
        - Extract `submissionTimestamps` (array of Firestore Timestamps).
        - Filter timestamps within last 24 hours (`now - t < 24 * 60 * 60 * 1000`).
        - Filter timestamps within last 10 minutes (`now - t < 10 * 60 * 1000`).
        - If 24h count >= 10: throw `HttpsError('resource-exhausted', 'Daily submission limit reached. You may submit up to 10 restrooms per 24 hours.')`.
        - If 10m count >= 3: throw `HttpsError('resource-exhausted', 'Submission burst limit reached. Please wait a few minutes before submitting another restroom.')`.
     3. **Atomic Commit:**
        - Write `/restrooms/${command.restroomId}` with `status: 'unverified'` and zero initial aggregates.
        - Write `/contributions/restroom_${command.restroomId}` with `moderationState: 'pending'` and `userUid: context.auth.uid`.
        - Write `/contributionRateLimits/${context.auth.uid}` with updated and pruned `submissionTimestamps`.
3. Add unit and emulator tests in `functions/test/` verifying:
   - First submission succeeds and initializes rate-limit record.
   - 3 submissions within 10 minutes succeed; 4th is rejected with `resource-exhausted`.
   - 10 submissions within 24 hours succeed; 11th is rejected with `resource-exhausted`.
   - Expired timestamps (> 24h) are pruned automatically.
   - Idempotent retry with identical `command.restroomId` succeeds without incrementing counter.
   - Unauthenticated or forged calls are rejected.

### P2.6-B — Flutter Mutation Adapter Integration
1. Extend `FirestoreMutationAdapter` or implement `CallableFirestoreMutationAdapter`:

   - In staging/production: invokes `submitRestroom` callable function.
2. Preserve existing `MainShellScreen` single-flight lock, draft preservation, advisory duplicate scan notes, and truthful error mapping:
