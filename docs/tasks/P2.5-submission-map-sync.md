## 2. Existing implementation to reuse

- `AddRestroomNotifier.validateAndPrepare()` allocates `restroomId` exactly once for a logical draft, including restored drafts.
- `AddRestroomFormScreen` returns a `CreateRestroomCommand` to `MainShellScreen`.
- `MainShellScreen._processDraftSubmissionFlow()` performs the P2.4 duplicate scan; its no-match and acknowledged-warning branches currently display P2.5 placeholder SnackBars and clear draft state.
- `FirestoreRestroomRepository.submitRestroom(command)` already performs one atomic `restrooms/{id}` + private `contributions/restroom_{id}` batch and ambiguity reconciliation. **Do not rewrite this mechanism without a demonstrated defect.**
- `FirebaseAuthRepositoryImpl.ensureAnonymousSession()` establishes an anonymous UID; `AuthNotifier.signInAnonymously()` currently catches errors and sets `AuthStatus.error`, so the caller must check authenticated state after invoking it.
- `MapDiscoveryNotifier.refreshCurrentViewport(bounds, zoom)` is the authoritative forced discovery refresh; `MapDiscoveryScreen` already implements focus-intent camera execution/recovery.
- `main.dart` currently silently falls back to seeded `InMemoryRestroomRepository` on Firebase init exceptions; this is acceptable for explicit offline development/test but must **never** masquerade as a successful remote save in staging.

## 3. Required implementation contracts

### P2.5-A — Staging runtime & identity safety

1. Distinguish production Firebase and explicit offline-development modes. In staging, fail visibly and keep submission unavailable when Firebase initialization or required config fails; do **not** write to a fallback in-memory repository while presenting the action as saved to Firestore.
2. Treat `APP_ENV=staging` as an application safety gate, not a security boundary. Explicitly block production submission until P2.6; retain server-side enforcement for production.
3. Before each submission attempt, guarantee a valid anonymous Firebase session through the existing `AuthRepository` abstraction (or `AuthNotifier` with checked resulting state). Handle sign-in failures without writing, losing form/draft data, or claiming success. Normal map discovery remains accessible.
4. Do not expose contributor UID in public restroom payloads or UI, persist movement/location history, or introduce new paid APIs.

### P2.5-B — Single-flight submit and recoverable failures

1. Reuse the **identical** normalized `CreateRestroomCommand` and `restroomId` through the first attempt and every retry after ambiguous errors. Never re-run ID allocation during retry.
2. Replace P2.4 placeholders in BOTH: (a) no-duplicate / partial-scan / query-error fail-open path and (b) explicit `No, It's a Different Restroom` path. The latter requires explicit acknowledgement before submission; sheet dismissal continues to preserve the draft.
3. Prevent duplicate gestures and parallel submissions across forms, sheets, and retries; show progress; disable actionable submission controls during flight.
4. Preserve the command on offline, network, permission, App Check, unknown-acknowledgement, and reconciliation failures. Provide visible `Retry` (same command), `Edit`/resume, and safe cancel/dismiss behaviors. No automatic retry loop.
5. Display errors accurately: network offline; permission/App Check/unauthorized (without falsely attributing all permission denials to App Check); invariant corruption requires distinct non-retry-as-new-ID handling. Do not clear the draft until confirmed successful save or deliberate discard.
6. On success, clear the exact submitted command, show truthful success feedback only after remote commit success or valid reconciliation, and do not double-present UI on repeated acknowledgments.

### P2.5-C — Canonical discovery synchronization

1. After confirmed submit, switch to Map tab, focus the submitted coordinates at zoom **16.5**, obtain the actual viewport via map idle/controller, and force the canonical discovery query even for equivalent cached viewport descriptors.
2. Select the new restroom **by command.restroomId only after it is returned by authoritative discovery**; no permanent optimistic or synthetic insertion to `_discoveredRestrooms`.
3. Open exactly one `RestroomPreviewSheet` showing **Unverified**. Guard map controller initialization, async stale generations, disposal, concurrent navigation, query failures, and results that omit the new record due to incomplete query or backend timing. Never claim a successful map refresh when not observed; offer explicit recovery.
4. Maintain the existing discovery, filter reset, selection ownership, P2.4 focus-token and snackbar-recovery contracts. Avoid unnecessary paid APIs and unbounded Firestore reads.

### P2.5-D — Testability and owner staging QA

Add targeted tests for:
- anonymous session present, absent, sign-in failure, and mid-session invalidation;
- staging Firebase initialization failure does not result in a fake in-memory success;
- no-match, query-error, partial-scan fail-open, duplicate explicit proceed, duplicate view-existing, dismissed-warning/resume, and stable ID;
- single-flight/double tap, lost acknowledgement with valid pair reconciliation, network error with public absent, partial/mismatched pair invariant failure, retry with identical command and no duplicate writes;
- success camera zoom 16.5 and forced authoritative viewport reload, exact ID selection and single Unverified preview, absent/degraded/stale query and camera unavailable paths;
- button states, accessibility, messages, teardown races and error recovery.
Retain existing P2.1 repository/rules tests; run smallest targeted suites first, then mandatory `dart format --output=none --set-exit-if-changed lib test`, `flutter analyze`, `flutter test`, `npm --prefix rules_tests run test:emulators`, `git diff --check`. Build Android/iOS if tooling is available; report `NOT RUN` rather than assuming results.
